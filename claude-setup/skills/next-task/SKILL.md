# Задание очереди

Ты работаешь автономно: человека рядом нет, спросить некого. Решай сам и записывай решения
в `docs/progress.md`.

Задание — не один пункт, а **сессия**: пачка пунктов одного куска работы. Контекст собирается
один раз на всю сессию, а дальше пункты идут по очереди. Ради этого сессии и заведены — не трать
ходы на повторное «осмотреться» между пунктами.

## 1. Узнай задание

Прочитай `.queue/current.md`: там вид задания (сессия или рубеж), этап, список пунктов
и строки-подсказки «Читать», «Опора», «Осторожно», «Сначала тесты».

Файла нет (ручной запуск) — найди в `docs/plan.md` первую сессию с пунктами `- [ ]`;
если пунктов не осталось, выполни первый непройденный рубеж. Этап 0 — не задание очереди
(его закрывает человек с Claude интерактивно); `run-queue.ps1` до его закрытия не стартует.

## 2. Собери контекст — один раз, по списку

1. `CLAUDE.md` — уже загружен.
2. `docs/map.md` — где что лежит и как добавляется типовая вещь (рецепты: инструмент, аннотация,
   диалог, настройка, сцена, тест на корпусе, команда и клавиша, `OT_FEATURE`). **Читай его первым**,
   до поиска по коду. Затем раздел «Правила работы» `docs/plan.md` (поиском по заголовку, только его).
3. Разделы `docs/design.md` из строки «Читать» — **только их** (поиском по заголовку `### 3.4`,
   `### 9.3` и т. п.). Эталон большой (~270 КБ); целиком он не нужен. `docs/tech-facts.md` (~320 КБ) —
   только поиском по теме (`Grep`), никогда целиком.
4. Файлы из строки «Опора» — образец рядом, писать с нуля почти никогда не надо.
5. `docs/progress.md`: раздел «Нужна ручная проверка» и две последние записи журнала — `Read`
   с `offset` ближе к концу файла; целиком журнал не читай.
6. `git status`, `git log --oneline -5` и хвост `.queue/workflows.log`: прошлая сессия могла
   оборваться на середине — тогда продолжи её. Отметки `[x]` в плане показывают, что уже сделано.

Что **не** делать: не перечитывать эталон целиком, не обходить `src/` подряд, не открывать файлы
«на всякий случай», не читать `build/`. Нужного места не видно — сначала `docs/map.md`, потом
поиск по имени (`Grep`).

## Команды проекта

Все команды — из корня репозитория. Окружение (`QT_QPA_PLATFORM=offscreen`, `OTTISK_PYTHON`,
`VCPKG_ROOT`, `QT_ROOT`, `MUPDF_ROOT`, `TESSDATA_PREFIX`, `OTTISK_INSTANCE=test`) ставит
`.claude/settings.local.json`. `cl`, `cmake`, `ctest`, `ninja`, `clang-format` есть только после
`tools\vcenv.cmd` (в `PATH` машины их нет) — поэтому сборка идёт через `tools\build_lock.ps1`, а остальное —
через `cmd /c "tools\vcenv.cmd && …"`. Команды ниже — для инструмента **PowerShell**; в Bash (Git Bash)
`cmd /c` превращается в `cmd C:/` и молча открывает пустой `cmd` — там писать `cmd //c "…"`.

- **Сборка своей цели:** `powershell -NoProfile -ExecutionPolicy Bypass -File tools\build_lock.ps1 -Target <цель>`
  (замок `.queue/build.lock` — один Ninja за раз, `vcenv` внутри, лог `build/debug/build.log`, при ошибке — хвост).
  Цели: `ottisk_core`, `ottisk_services`, `AcroBatya`, `unit_tests`, `ui_tests`, `engine_tests`, `render_tests`,
  `e2e_tests`, `imgcmp`, `render_refs`, `bench`. Ошибки — `Select-String -Path build\debug\build.log -Pattern 'error C|error LNK|FAILED' | Select-Object -Last 40`.
- **Тесты рядом с правкой:** `cmd /c "tools\vcenv.cmd && ctest --test-dir build/debug -R <регекс> --output-on-failure"` или прямо
  `build\debug\bin\unit_tests.exe --gtest_filter=<Набор>.* --gtest_brief=1` (тому, кто запускает exe из
  `build`, нужен `C:\Qt\6.12.0\msvc2022_64\bin` в `PATH`: `$env:PATH = "C:\Qt\6.12.0\msvc2022_64\bin;$env:PATH"`).
  Быстрый набор: `cmd /c 'tools\vcenv.cmd && ctest --test-dir build/debug -L "^(unit|ui)$" -LE slow -j 12 --timeout 60 --output-on-failure --no-tests=error'`.
- **Полная проверка:** `py -3.14 tools\verify.py` — на переднем плане (configure при нужде, сборка,
  `clang-format --dry-run --Werror` и стражи параллельно, ctest по меткам; печатает только упавшее; код 0 — зелёный).
  Инкрементально 2–6 минут, после смены PCH 10–15 — таймаут команды до 30 минут (`BASH_DEFAULT_TIMEOUT_MS`).
- **Формат:** `cmd /c "tools\vcenv.cmd && clang-format -i <файлы>"`.
- **Снимки:** сцена — функция в `src/ui/shots/scenes.cpp` и строка в таблице сцен там же (эталон 6.10 зовёт её `SCENES`); снять — `powershell -NoProfile -ExecutionPolicy Bypass -File tools\shots.ps1 -Only <имя>[,<имя>] [-Theme dark]`
  → `.queue/screenshots/<имя>.png`; **посмотреть PNG** (`Read`).
- **Python над PDF, корпусами и скачанным** — только `"$env:OTTISK_PYTHON" -X utf8 -I <скрипт>`
  (venv `C:\Tools\venv-test`; `-I` не видит `PYTHONUTF8`, поэтому `-X utf8`). `py -3.14` — только `tools\verify.py`.
- **Сборка выпуска** — `tools\build.ps1` — только рубеж и сессия 9.4.
- **Коммит и отметка:** `node .claude/skills/next-task/done.mjs "этап N: что сделано" "<кусок текста пункта>"`.

## 3а. Сессия — сделай все пункты

Для каждого пункта по очереди:

1. Сделай **только** этот пункт. Логика без интерфейса (`core`, а в XL-сессиях — обязательно) —
   **сначала тесты**: gtest-файл с `TEST(...)` и ожиданиями (для XL — JSON на фикстурах) до кода;
   тест, закрывающий ID каталога, пишет `OT_FEATURE("<id>")`. Новый файл кладётся в каталог своей цели
   (`src/core/...`, `src/services/...`, `src/ui/...`, `tests/unit/...`) — его подхватывает
   `file(GLOB_RECURSE … CONFIGURE_DEPENDS)`, CMake **не правится**. Новые каталоги, цели, PCH и
   `CMakeLists.txt`/`cmake/*.cmake` меняет только главный исполнитель сессии, и только если пункт этого требует.
2. Собери свою цель и прогони тесты рядом с правкой (команды выше). Весь набор на каждом пункте
   гонять не нужно — он в конце сессии.
3. Коммит и отметка — **одной командой** из корня репозитория:
   `node .claude/skills/next-task/done.mjs "этап N: <короткое что сделано>" "<кусок текста пункта>"`.
   Она делает `git add -A` и коммит, а потом меняет `- [ ]` на `- [x]` у пункта, в котором есть
   этот кусок (кусок должен быть однозначным — иначе ошибка и ничего не отмечено). Текст пункта не трогай.
   Отметка ставится после коммита, а не в конце сессии: если сессия оборвётся, сделанное не пропадёт.
4. Пункт отмечается `[x]`, если его **собственный результат** сделан: код, `Fake*`-реализация, тесты
   на фикстурах. То, что можно проверить только вживую (экран, принтер, сканер, Acrobat Reader,
   настоящий сертификат, LibreOffice, сеть), — строкой в «Нужна ручная проверка» `docs/progress.md`
   с номером сессии и тем, что именно проверить; это не повод для `[~]`. `--manual` (отметка `[~]`)
   и `QUEUE: NEEDS_HUMAN` — **только** когда результат пункта без человека невозможен вообще
   (как 10.1: замечания пилота пишет человек).

Следи за ходами. Осталось меньше четверти — не начинай новый пункт: доведи текущий,
закоммить, отметь, запиши в журнал и ответь `QUEUE: PARTIAL`. Очередь продолжит с остатка
новой сессией, и это дешевле оборванной попытки.

Когда пункты кончились:

5. Полные проверки: `py -3.14 tools\verify.py`. Упало — чини и перезапускай **только упавшее**
   (сборку цели, `ctest -R`, `clang-format -i`, страж `"$env:OTTISK_PYTHON" -X utf8 -I tools/<страж>.py --root .`),
   а `verify.py` целиком — ещё один раз, в самом конце. Красный по PCH после правки `CMakeLists.txt`
   или PCH (`src/{core,services,ui}/pch.h`) — один раз `cmd /c "tools\vcenv.cmd && cmake --build build/debug --target clean"`, потом `verify.py`.
6. Сессия построила или изменила экран или диалог — допиши сцену в `src/ui/shots/scenes.cpp`
   (главные — и в тёмной теме), сними **только свои** сцены (`tools\shots.ps1 -Only …`) и **посмотри снимки**
   (`Read` файла `.queue/screenshots/<имя>.png`), сверив с разделом 6 `docs/design.md`: размеры 48/320/44/280/32,
   токены, Segoe UI, кириллица видна, иконки. Пиксельного эталона у сцен нет; расхождение чинится в токенах
   или компоненте, а не в сцене.
7. `CHANGELOG.md`, раздел «Не выпущено» — одна строка «что видно человеку» на сессию.
8. Одна запись в конце `docs/progress.md` — на всю сессию, а не на каждый пункт:

```markdown

```

## Быстро

- **Независимое — одним сообщением.** Несколько файлов прочитать, несколько поисков — параллельными
  вызовами в одном ответе, а не по одному.
- **Не ждать паузой.** Никаких `sleep` / `Start-Sleep` «на всякий случай».
- **Сессия очереди — это один ответ.** Её запускает `claude -p`: закончил ответ — сессия закрыта,
  фоновые команды убиты, а очередь засчитает неудачу. Поэтому `verify.py`, тесты, `shots.ps1` и
  сборки — **на переднем плане** с таймаутом до 30 минут. В фоне — лишь то, что дольше 30 минут
  (линковка Release с LTCG, первый configure с vcpkg), с выводом в лог, и до ответа дождаться
  его **блокирующей** командой (`Wait-Process`, цикл `until` с таймаутом). Фраза «ещё идёт, подведу
  итог позже» — всегда ошибка: итог подводится в этом же ответе.
- **Короткий вывод.** Сборку — в лог и `Select-String` по ошибкам; ctest — `--output-on-failure`,
  без `-V`; gtest — `--gtest_brief=1`; длинное — хвостом (`| Select-Object -Last 40`).
- **Не перечитывать.** Прочитанный в этой сессии файл целиком второй раз не читается — только
  нужный кусок с `offset`. Эталон — только разделы из строки «Читать».
- **Субагенты — только на объём** (пачка однотипных диалогов, фикстуры, тексты, переводы по частям),
  не на поиск и не на «осмотреться» — на это есть `docs/map.md`. Субагенты не коммитят и не запускают
  `verify.py` и сборку (кроме случая «единственный исполнитель», раздел «Ultracode»).
- **Сначала закончить, потом полировать.** Всё по пунктам — и сразу `verify.py`, а не круги
  «ещё немного улучшу» до проверок.
- **Qt — без окна.** Тесты и сцены идут с `QT_QPA_PLATFORM=offscreen` (глобальный `env` очереди);
  окно на экране человека открывает только рубеж (`--smoke 8` с `$env:QT_QPA_PLATFORM=''`), на секунды.
- **Сборки:** рабочая — `build/debug`; `build/release` — только рубежи, 9.4, сессия 1.1 (`render_refs`)
  и 1.2 (`bench`); Release-цели — только `AcroBatya render_refs render_tests bench`.
- **Опора уже сверена.** Строки «Опора» и «Осторожно» плана проверены перед запуском очереди:
  не перепроверяй их обходом папок — открой названные файлы и начинай.

## Ultracode (только если очередь запущена с `-Effort ultracode`)

По умолчанию (решение человека 23.10.2026) очередь идёт на Opus 5.5 с `--effort xhigh`: workflow не нужны, субагенты
(инструмент Agent, без фона) — по правилам раздела «Быстро»; правила ниже про «один исполнитель на файлы»,
сборку и запреты для агентов действуют и для них. Если человек запустит очередь с `-Effort ultracode` (сессия идёт с `--effort ultracode`): Claude Code подгружает навык workflow-authoring и
предлагает workflow для каждого шага. Workflow и фоновые агенты досчитываются после хода: очередь
даёт до 2 часов ожидания (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=7200000`). Чтобы работа не терялась
и не ломала репозиторий:

- **Workflow всегда идёт в фоне.** Вызов сразу отвечает «launched», результат приходит уведомлением
  в новом ходе. В ходе запуска не считать работу сделанной: не коммитить, не ставить `[x]`,
  не писать журнал и не печатать строку `QUEUE:`. Сразу после запуска записать `runId`, путь скрипта
  и id задачи строкой в `.queue/workflows.log` — оборванную сессию можно продолжить
  `Workflow({scriptPath, resumeFromRunId})`.
- **Файлы правит один исполнитель за раз.** Параллельные агенты — на чтение, разведку, ревью и
  проверку находок; правки кода — один агент на набор файлов без пересечений (переводы — по частям
  `i18n/en-parts/`). Новый файл агент кладёт в каталог своей цели (GLOB) — правка CMake не нужна.
  Главная сессия после workflow читает итог, сама сверяет `git diff` и только потом коммитит через `done.mjs`.
- **Агенты workflow не запускают** `cmake --build` (кроме случая ниже), `tools/verify.py`,
  `tools/shots.ps1`, `tools/build.ps1` — в `build/debug` один Ninja за раз (замок `.queue/build.lock`);
  **не правят** `CMakeLists.txt`, `cmake/*.cmake`, `CMakePresets.json`, PCH (`src/core/pch.h`, `src/services/pch.h`, `src/ui/pch.h`), `docs/plan.md`,
  `docs/progress.md`, `CHANGELOG.md`, `tests/render/expected/`; **не коммитят**, не трогают `.queue/`,
  теги, `%LOCALAPPDATA%\AcroBatya` человека и `C:\Qt`, `C:\src\mupdf`, `%LOCALAPPDATA%\vcpkg`, `C:\Tools`.
- **Цикл сборки для C++-исполнителей** (иначе ни один агент не может скомпилировать свой код, а главная
  сессия чинит чужие ошибки сама):
  1. главная сессия после workflow запускает `tools\build_lock.ps1 -Target <цели пункта>`
     (= `cmake --build build/debug --target …` под замком);
  2. в `build/debug/build.log` есть `error C` / `error LNK` — выдержку (файл:строка: ошибка) получает
     **тот же исполнитель** вторым шагом workflow с задачей «исправь только эти ошибки»; не более 2 кругов,
     дальше главная сессия чинит сама или отвечает `QUEUE: PARTIAL`;
  3. агент собирает сам **только если он единственный исполнитель в сессии**, и только свою цель —
     `tools\build_lock.ps1 -Target <lib|test_exe>`; тесты рядом со своей правкой (`ctest -R`) ему тоже можно;
  4. при двух и более исполнителях сборка — только главной сессией после слияния правок: общий PCH и
     unity-группы в одном `build/debug` иначе собираются по полуправленным файлам соседа.
  Полный `cmake --build`, `verify.py`, `shots.ps1` — только главная сессия.
- **Удачные шаблоны:** понять кусок кода параллельными читателями → один исполнитель на набор файлов →
  цикл сборки → независимые проверяющие ищут ошибки в `git diff` (каждую находку — опровергнуть) →
  главная сессия чинит, гоняет проверки, коммитит. Для рубежа — параллельные проверяющие по экранам
  и критериям, каждую находку — подтвердить вторым агентом, прежде чем править.
- **Последний ход — только когда в фоне ничего не осталось**: ни workflow, ни агентов, ни команд.
  Строка `QUEUE: …` — в последнем ходе (очередь видит только его текст).
- **Ходы.** Уведомления о завершении фоновой работы тоже идут ходами; при четверти ходов в запасе —
  не запускать новых workflow, закончить текущий пункт и ответить `QUEUE: PARTIAL`.

## 3б. Рубеж — проверь этапы

Рубеж проверяет один или несколько этапов сразу. Его задача — не переделывать работу сессий,
а поймать расхождения с эталоном и стыки между этапами (эталон 9.6).

1. `py -3.14 tools\verify.py --full` (Debug целиком); Release — `py -3.14 tools\verify.py --preset msvc-release --labels "render|bench"`
   (цели `AcroBatya render_refs render_tests bench`; LTCG-линковка долгая — в фоне с логом и блокирующим ожиданием).
2. ASan: пресет `msvc-asan`, `unit|engine` под ASan. Фаззер 10 минут: пресет `msvc-fuzz`,
   `pdf_open_fuzzer -max_total_time=600 -rss_limit_mb=4096 -timeout=20`; падения → `tests/fixtures/regress/`
   и тест `unit.regress.load`.
3. bench: `"$env:OTTISK_PYTHON" -X utf8 -I tools/bench_compare.py docs/bench/baseline-<прошлый>.json build/bench/*.json`
   (+25 % медианы — красный), итог — `docs/bench/baseline-r<N>.json`.
4. **Снимки:** `tools\shots.ps1 -All`; контакт-листы `"$env:OTTISK_PYTHON" -X utf8 -I tools/review_refs.py --shots --sheet 16`;
   поштучно (`Read`) — сцены с pHash-расстоянием > 8 к `.queue/shots-prev/` и 30 главных сцен `tools/main_scenes.txt`,
   против раздела 6 эталона. Сцены не хватает — допиши её: она пригодится следующему рубежу.
5. **Окно на экране:** один раз `$env:QT_QPA_PLATFORM=''; build\release\bin\AcroBatya.exe --smoke 8 -platform windows`
   (с `C:\Qt\6.12.0\msvc2022_64\bin` в `PATH`): код 0, в stderr нет «Could not load the Qt platform plugin».
   Больше ничего на экране не открывать.
6. Скрипт `tools/verify_r<N>.py` (`"$env:OTTISK_PYTHON" -X utf8 -I`, в Git; журналы и артефакты — `.queue/r<N>/`)
   по строкам «**Проверка:**» этапов и критериям контрольной точки M; действия — через `--script` сессий-владельцев.
   Корпуса рубеж не качает: нет тега — `SKIP` и строка в «Нужна ручная проверка».
7. `tools/scope_report.py` — «закрыто N из M»; `tools\lint.ps1 -All`; пресет `msvc-analyze` +
   `"$env:OTTISK_PYTHON" -X utf8 -I tools/analyze_summary.py` — новых предупреждений против `docs/analyze-baseline.json` нет.
8. **Установщик:** `git diff --stat v0.N.0 HEAD -- src tools installer assets i18n` пуст — не пересобирать;

## 4. Заверши

Последней строкой ответа — ровно одно:

- `QUEUE: DONE` — все пункты сессии сделаны (или рубеж пройден), проверки зелёные;
- `QUEUE: PARTIAL <сколько сделано и что осталось>` — часть пунктов готова и отмечена,
  очередь продолжит с остатка;
- `QUEUE: NEEDS_HUMAN <что нужно>` — результат оставшегося пункта без человека невозможен вообще
  (как 10.1 до пилота); живые проверки сделанного — не сюда, а строкой в «Нужна ручная проверка»;
- `QUEUE: BLOCKED <причина>` — дальше нельзя (сломана среда: `cl` не найден, диск, `C:\Tools`; нужна новая
  библиотека или смена стека; противоречие в документах). Перед этим закоммить всё полезное.

Очередь считает не вердикт, а отметки в плане: отмеченные пункты не пропадают ни при каком итоге.
